## Evidence and causal limits

`125036cb61a9d15d624f5d1c8a0c65d69076574c` completed five application stages
and reached checkpoint 11, then exited 1. Its terminal state reported only
`finders:true`; the other nine comparisons were false. This establishes a
finder-list mismatch during the first vLLM import, **not the identity of that
finder or the cause of the earlier GPU startup failure**. Original run files
are preserved separately by the parent, not regenerated by this task.

The pinned vLLM source installs `_PatternMatcherPatchFinder` for Torch below
`2.16.0.dev` when `torch._inductor.pattern_matcher` is not already imported.
That finder inserts itself ahead of the sealed finder, removes itself on the
target import, and wraps the target's loader to apply a dtype fallback patch.
This is a concrete source-backed compatibility conflict with the unchanged
finder invariant. The tests reproduce it with the exact Apache-2.0 registration
function and synthetic dependency modules, without importing vLLM or Torch.
They do not prove that the actual observed finder was this one.

## Narrow behavior

The lab's source-only loader verifies the complete vLLM source and changes
exactly one AST call from `_patch_inductor_pattern_matcher()` to a private
registration callback. The original version condition, patch implementation,
and all other statements remain intact. The temporary callback name is removed
after module execution.

Registration never changes `sys.meta_path`. Instead, the existing sealed finder
loads only the exact selected-root Torch target from freshly verified source.
It applies vLLM's unchanged callback after that load, or immediately if that
same loader already completed the target. It neither eagerly imports Inductor
nor skips the fallback patch. No unrelated finder or module receives permission.

Source reads retain the existing bounded, no-follow, regular-file checks.
Cached bytecode is not executed. Wrong source, version, origin, preloaded target,
partial/cached target substitution, reload, missing target, execution failure,
callback failure, and post-load boundary failure reject. A failed target or
registration latches the adapter closed, even if an upstream caller catches
the initial exception; retry cannot turn it into a pass. The target may not be
removed or replaced after a verified load.

The same bootstrap applies before spawn unpickling and in fresh reentry.
The ordinary worker-method, paths, executable, no-site, environment and finder
invariants remain enforced. CPU evidence remains software-only and cannot
authorize serving. Serving still requires its separate reviewed operation and
hardware/weight gates; this change grants none of them.
